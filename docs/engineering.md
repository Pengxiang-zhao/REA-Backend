# REA-Backend Engineering Specification

**Status:** Engineering preview; the standalone package is in preparation.

**Date:** October 18, 2026.

## 1. Purpose and scope

REA-Backend accepts the source code or APK of an existing Android client. Agents investigate the server behavior required by that client, produce a reviewable backend software requirements specification (SRS), and implement an independent service using the specification and evidence collected through the same input route. Protocol, storage, and real-client checks validate the declared scope.

The project produces two kinds of deliverables: a reusable method and toolset, and the requirements and backend package generated by an individual run. The initial open-source release focuses on the method and toolset. Users can store, deploy, and distribute their generated services separately.

### Success criteria

A complete build should make the following clear: which inputs were provided; which requirements were discovered; which rules remain unknown; what was implemented; which build the real client connected to; which checks passed; where failures and deferred work are recorded; and how another person can reproduce the result.

Success applies only to the explicitly declared and validated feature scope. An endpoint returning success, a response matching a schema, a client consuming that response, and the resulting business state satisfying a requirement are distinct outcomes.

### System boundary

The current target is a backend compatible with an Android client. The client may use an existing server-address setting or require a documented connection adaptation. Any repackaging, signing changes, or network-configuration changes—and their effects—must be recorded. Regenerating an entire frontend is outside the current core deliverable.

The project reconstructs interfaces and behavior supported by authorized materials. It does not recover hidden server source code or promise coverage of algorithms and business rules that the client does not expose. Unknowns are recorded as gaps. Any local policy needed to proceed is declared separately.

## 2. Two input routes

| Aspect | Source route | APK route |
|---|---|---|
| Required input | Android client source pinned to a specific version | APK pinned to a specific version |
| Primary analysis material | Request construction, data models, response parsing, UI and background calls, authorized SDKs | Analysis-tool execution records, decompiled or decoded material, resources, configuration, protocol strings, traceable calls |
| Optional material | Dependencies, documentation, and runtime observations explicitly authorized in the configuration | Decompiler output, documentation, and runtime observations explicitly authorized in the configuration |
| Input provenance | Source revision, paths, and hashes | APK identity and hash, tool versions, invocation parameters, and limitations |
| Subsequent stages | Shared analysis records, SRS, independent review, implementation, and validation | Same stages as the source route |

The APK route must not read the other route's client source, SRS, or reference implementation. Original server source, reference answers, and unauthorized feedback are excluded from the default inputs. Authorized runtime observations must identify the observed system, the time of observation, and the information source.

If a comparison requires a matched source/APK pair, verify that the inputs correspond to the same version or build. Matching version labels alone do not establish equivalence. This requirement does not prevent either route from running independently.

## 3. Roles and tool boundaries

| Role or component | Responsibility |
|---|---|
| Analysis and requirements agent | Read materials, collect additional evidence, maintain analysis records, and identify requirements and gaps |
| Independent reviewer | Select samples from authorized originals, reconstruct critical behavior chains, and review the relationship between requirements and evidence |
| Implementation agent | Use the reviewed SRS and evidence from the same route to write the service, scenarios, tests, and implementation mapping |
| APK inspection and decoding tools | Provide client-analysis capabilities, raw results, and recorded limitations |
| Pipeline CLI | Validate structures and references, freeze hashes and versions, package artifacts, execute explicit validation plans, and record outputs |
| User | Define the target, scope, permitted inputs, and runtime conditions; receive the results and outstanding work |

Roles may run in separate agent sessions and do not depend on a particular model provider. Review independence must be supported by the actual workflow. A validator can inspect records and bindings, but a role field cannot prove independent reasoning.

A host coding agent performs analysis and programming. The CLI validates and packages the resulting artifacts and executes explicit checks. The generated backend runs independently of the analysis tools and coding agent.

## 4. Stages and handoffs

### Stage A: Pin inputs and prepare materials

Establish the app identity, input route, version, authorized materials, and target scope. For the APK route, inspect and decode the package, collect analysis evidence, and preserve complete execution records and limitations.

A successful preparation step only establishes that materials are ready. If endpoint extraction returns no results, investigate the collection method and client implementation before concluding that the app has no backend.

**Handoff:** Input configuration, input identity, preparation report, and raw-evidence locations.

### Stage B: Explore behavior and maintain analysis records

Investigate UI entry points, background jobs, protocol calls, data models, and dependencies. Each work item records its question, related evidence, findings, contract checks, and boundaries that remain untraced. Collect additional evidence according to the risks found instead of repeatedly collecting the same package-level summary.

The investigation addresses five kinds of questions:

1. **Response consumption:** Which fields affect rendering, branches, loops, and subsequent requests? How do missing values, nulls, empty lists, and defaults differ?
2. **Transport conversions:** How are request encodings, numbers, times, and identifiers transformed between transport, storage, and consumption?
3. **Business state:** What does an action change, how is that change read back, and what happens after a retry, failure, or restart?
4. **Resource consumption:** Can the actual consumer parse and use images, article content, audio, attachments, and other resources?
5. **Complete workflows:** What prerequisites, dependencies, concurrent jobs, caches, and stopping conditions apply to the default entry points?

The shared method requires these boundaries to be investigated. Concrete fields, timeouts, limits, status codes, and business rules still come from the current evidence. A missing answer must not be filled with another app's behavior.

**Handoff:** Continuously revised analysis records, evidence references, contract and workflow records, and unknowns.

### Stage C: Resolve recorded work and freeze the baseline

Assign every registered work item an explicit disposition: `answered`, `blocked`, or `out_of_scope`. Contract checks, flow traces, and flow boundaries use `answered`, `blocked`, or `not_applicable`. Do not silently delete unresolved records. Blocked items retain their gaps and next steps; uninvestigated items cannot be marked as answered. Once settlement checks pass, freeze the input manifest, analysis revision history, and method files.

Settlement checks apply only to registered content. Independent review and runtime validation must still look for omissions that were never registered.

**Handoff:** Frozen inputs, analysis snapshot and history, and method manifest with hashes.

### Stage D: Write the SRS and obtain independent review

The SRS describes the capability inventory, functional requirements, data models, interface contracts, state transitions, quality requirements, and acceptance criteria. Each requirement links to evidence and unknowns, distinguishing direct observations, inferences from client behavior, and local design decisions.

The reviewer independently selects critical original materials and risky behavior chains. The review records reconstructed behavior, comparisons with the author's findings, issues found, and unread scope. After revisions, the review record is bound to the final files.

The SRS may include modules that cannot yet be implemented. Selecting a narrower implementation scope preserves the remaining requirements and gaps.

**Handoff:** SRS document, machine-readable index, input manifest, run record, frozen analysis and method files, and review record.

### Stage E: Implement and validate an initial complete workflow

Start with the selected workflow's actual entry or login, one key operation, persistence, and a subsequent read. Include retries where they are part of that workflow. Connect the pinned client to this build early to expose protocol and response-consumption mismatches.

All SRS requirements retain an implementation mapping and may be declared implemented, partially implemented, or deferred. Local policies reference the original gaps and must not be presented as recovered rules from the original server.

**Handoff:** Service code, dependencies, seed data, implementation mapping, initial build, and real-client validation records.

### Stage F: Expand, validate the final build, and deliver

Expand the implementation within the selected scope and run HTTP, storage, resource, and real-client checks. Final validation is bound to the final build and references passing early records under the same complete SRS baseline. Earlier success does not replace final checks.

Deliver a service that runs independently, together with provenance, requirements, implementation, and validation records. Generate data and credentials during deployment; do not hardcode the developer's machine address in instance configuration.

**Handoff:** Build package, startup instructions, validation report, unfinished scope, and known limitations.

## 5. Recovery from failures

| Cause | Response |
|---|---|
| Requirements gap | Return to evidence collection and the SRS within the same route; create a new requirements baseline and preserve the previous records |
| Implementation defect | Repair the implementation and affected checks under the current requirements, then produce a new build |
| Environment issue | Repair tool, device, network, or service-startup conditions, then rerun the affected checks |
| Unknown cause | Preserve the failure and continue investigating without prematurely inferring a business rule |

A changed SRS baseline requires corresponding early validation to be re-established. Every repair preserves previous failures, builds, and version relationships.

## 6. Artifacts and invariants

The workflow preserves the following artifacts. Exact public file formats and command interfaces will be documented with the standalone package.

| Artifact | Purpose |
| --- | --- |
| Input configuration | Pin the app, route, materials, and permissions |
| Analysis record | Store work items, evidence, contracts, workflow boundaries, and revision history |
| SRS run record | Bind input configuration, manifests, analysis, and method versions |
| Review record | Record independent sampling, issue disposition, and final-version bindings |
| Implementation manifest | Declare implementation status and local policies for each requirement |
| Build package | Preserve the service, SRS, analysis, method, and per-file digests |
| Validation plan | Link workflows, risk obligations, requirements, checks, and required evidence |

Review, implementation, and build records bind the SRS document and its index. Raw inputs are not copied into a build package by default. Users must retain authorized materials if they need to repeat analysis or review the inputs. All files and dependencies needed to run the service should be delivered.

### Keep three kinds of status separate

- **Requirements understanding:** What the evidence supports and what remains unknown.
- **Implementation declaration:** What the author claims to have implemented, partially implemented, or deferred.
- **Validation result:** Which checks ran against which actual build, inputs, and workflows.

A single `done` value must not combine these states. Report review approval, successful packaging, and business-validation results separately.

## 7. Reusable robustness mechanisms

| Mechanism | Problem addressed | Limitation |
|---|---|---|
| Bind input, tool, and method versions | Results cannot be attributed or reproduced | Hashes establish file identity, not evidence sufficiency |
| Resumable analysis and retained gaps | Long tasks lose context or unresolved work disappears | Unregistered omissions still require review of original materials |
| Independent sampling and behavior reconstruction | Review merely repeats the author's summary | Reviewers must actually read originals and record differences |
| Consumer checks and round trips across layers | JSON looks correct but the client cannot use it | Checks must follow the specific client's consumption rules |
| Early and final real-client validation | Compatibility problems emerge too late or results become stale after repairs | Each stage binds its own actual build and evidence |
| Retained failures and recovery by cause | Implementation patches conceal requirements errors | Attribution requires evidence; otherwise the cause remains unknown |
| Bounded execution and resource management | Device contention, port conflicts, and leftover processes | The runner is not a security sandbox |

Performance improvements should come from caching reusable static materials, targeted retrieval, parallel independent investigations, and automated execution and collection. Cache reuse must check identity and applicability. Cached results cannot replace required validation of a new build.

## 8. Initial release scope

The first release focuses on material preparation, analysis records, requirements freezing and review, implementation mapping, build packaging, and development validation. Android tools remain adapters for real-client validation. Successful data collection does not automatically establish correct business behavior.

The current implementation and examples are organized around Python services. Dependency and startup profiles for other languages have not been validated. The requirements method is language-independent; support for additional backend stacks requires deployment and client checks.
